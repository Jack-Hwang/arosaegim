# F1 도착 자동 스탬프

## 1. 한눈에 보기

차가 목적지 반경(120미터) 안으로 들어오면 운전자가 손을 쓰지 않아도 스탬프가 기록되는 기능입니다.
도착 판정은 두 단계입니다 — 1차는 근접 알림(에뮬레이터 실측 [확인]), 2차는 근접 알림이 실패했을 때 좌표로 거리를 직접 계산하는 폴백입니다.
도착이 인정되면 스탬프 → 방문 기록 → 전송 대기열 적재 → 도착 음성 → 다음 목표 감시와 내비게이션 경로 요청이 한 파이프라인에서 순서대로 일어납니다.
수용 기준 11건 중 에뮬레이터 실측 2건이 [확인], 1건이 [일부 확인], 단위 시험 6건이 [코드 확인], 2건은 (설계)입니다.
아직 미확인인 것: 근접 알림 실패 상황에서 폴백으로 전환되는 장면 자체는 실측에서 보지 못했고(AC02 정본 note), 도착 뒤의 길 안내 화면 표시도 미확인입니다(AC08 정본 note).

## 2. 목적과 범위

| 요소 | 내용 |
|---|---|
| 포함 | 근접 알림(반경 단위 미터) 등록과 ENTER 수신, 근접 알림 실패 시 좌표 거리 계산 폴백, 재진입·순서 위반·완주 뒤 도착의 무효 규칙, 방문 기록(장소 ID+시각 — 좌표 없음), 전송 대기열 적재와 전송 재시도, 프로세스 재시작 시 진행 복원, 코스 재시작 시 진행·기록 초기화, 도착 뒤 다음 목표의 내비게이션 경로 요청 |
| 제외 | 좌석 점유·주행거리 신호의 수집(별도 과제 A5), 서버의 방문 저장·같은 분 멱등 판정(F7 문서), 전송 대기열의 FIFO·멱등키·PIN 처리 세부(F9 문서), 도착 음성의 3단 재생 체인(F5 문서), 주행·정차 화면 전환(F2 문서) |
| 가정 | 반경 단위는 미터다 — SDK 자료형(float 미터)과 에뮬레이터 실측이 모두 확인(개발 기록 F6·F48). 도착 판정의 본역은 FusedLocation 근접 알림이다 — 내비게이션의 도착 콜백에는 장소 식별자가 없고 실측에서도 미발생이 관찰됐다(개발 기록 F8·F57). 수신 위치는 저장하지 않는다 — 메모리에만 존재(docs/ARCHITECTURE.md 4절) |
| 경계 | 도착 판정·스탬프·로컬 기록은 차량 앱의 몫이고, 방문 기록의 보관·조회는 서버의 몫이다(F7 문서). 코스는 경주 3곳(국립경주박물관·대릉원·첨성대) 순서를 따른다. 디버그 빌드의 '수동 도착' 버튼(ManualArrivalDetector)은 같은 파이프라인을 타는 진단 도구다 |

## 3. 입력·출력·상태

| 구분 | 항목 | 내용 |
|---|---|---|
| 입력 | 근접 알림 이벤트 | 목표 장소 좌표·반경으로 등록한 알림의 ENTER 전이 — 소스 app/src/main/java/app/arosaegim/pleos/FusedArrivalDetector.kt |
| 입력 | 위치 콜백 좌표 | 주행 화면의 거리 표시와 폴백 판정에 사용 — 저장하지 않음(AC03) |
| 입력 | 코스·시드 | 경주 3곳의 순서 정보 — assets/seed/seed.json |
| 출력 | 스탬프·진행 | StampEngine 판정 통과 시 스탬프 1건, 다음 목표 갱신(1/3 → 3/3) — 소스 app/src/main/java/app/arosaegim/domain/StampEngine.kt |
| 출력 | 방문 기록 | filesDir/visits.json에 장소 ID+시각 1건(좌표 필드 없음) — 소스 app/src/main/java/app/arosaegim/data/VisitStore.kt |
| 출력 | 대기열·경로 요청 | 전송 대기열 적재 후 전송 1회 시도, 다음 목표의 내비게이션 경로 요청(AC08) |
| 출력 | 화면·음성 | 주행 화면 거리 한 줄("약 1.9km" 실측 — 개발 기록 F49), 도착 음성 1문장 |
| 상태 | 코스 진행 | 현재 목표·스탬프 수·완주 여부 — 완주 뒤 추가 도착 신호는 무시하고 감시를 멈춤(AC06) |
| 상태 | 세션 수명 | TripSession은 Application 수명 — 어떤 화면도 세션을 stop하지 않음(docs/ARCHITECTURE.md 3절) |

## 4. 수용 기준

수용 기준은 EARS(요구를 다섯 모양의 한 문장으로 쓰는 방법)로 쓰여 있고, 아래 표는 정본 JSON에서 생성했습니다.

| 번호 | 유형 | 수용 기준 | 확인 방법 | 상태 |
|---|---|---|---|---|
| AC01 | 사건 | 목적지 반경 120m 안으로 들어오면 앱은 해당 장소의 스탬프 1건을 기록합니다. | 에뮬레이터 실측 | [확인] |
| AC02 | 금지 | 근접 알림 등록이 실패하거나 오류가 나면 앱은 수신 좌표로 거리를 직접 계산해 도착을 판정합니다. | 코드 확인 | (설계) |
| AC03 | 항상 | 앱은 위치 정보를 도착 판정과 화면 거리 표시에만 쓰고 저장하지 않습니다. | 코드 확인 | (설계) |
| AC04 | 사건 | 스탬프를 이미 찍은 장소에 다시 들어와도(재진입) 앱은 중복 스탬프를 기록하지 않습니다. | 단위 시험 | [코드 확인] |
| AC05 | 사건 | 코스 순서상 지금 목표가 아닌 장소에 도착해도 앱은 스탬프를 기록하지 않습니다. | 단위 시험 | [코드 확인] |
| AC06 | 상태 | 코스를 완주한 뒤에는 앱이 추가 도착 신호를 무시하고 도착 감시를 멈춥니다. | 단위 시험 | [코드 확인] |
| AC07 | 선택 | 차가 기어 D(주행) 상태인 경우에도 앱은 반경 진입을 감지해 도착을 기록합니다. | 에뮬레이터 실측 | [확인] |
| AC08 | 사건 | 도착 스탬프가 등록되면 앱은 다음 목적지로 내비게이션 경로를 요청합니다. | 에뮬레이터 실측 | [일부 확인] |
| AC09 | 사건 | 앱을 다시 시작하면 앱은 저장된 방문 기록으로 스탬프 진행을 복원합니다. | 단위 시험 | [코드 확인] |
| AC10 | 금지 | 네트워크가 없어 서버 전송이 실패해도 앱은 방문 기록을 먼저 차 안에 저장하고 전송은 나중에 다시 시도합니다. | 단위 시험 | [코드 확인] |
| AC11 | 선택 | 코스를 처음부터 다시 시작하는 경우 앱은 스탬프 번호를 1부터 다시 매기고 이전 방문 기록을 지웁니다. | 단위 시험 | [코드 확인] |

상태 분포: [확인] 2건 · [일부 확인] 1건 · [코드 확인] 6건 · (설계) 2건.

정본: [docs/spec/ac/f1_arrival.json](ac/f1_arrival.json)

표의 '확인 방법'은 정본의 verify.kind를 한국어로 옮긴 것입니다 — 단위 시험(앱 JVM 테스트), 서버 시험(backend pytest), 에뮬레이터 실측(Pleos Connect 에뮬레이터 실행 기록), 코드 확인(소스 코드 근거).
상태 어휘는 정본과 같습니다 — [확인]·[일부 확인]·[코드 확인]·[실패]는 시험·실측까지 끝난 정도를, (설계)는 코드로 구현됐으나 화면 실측이 남은 항목을 뜻합니다.

## 5. 입력→출력 예시

**첫 도착(AC01).** 진단 화면에서 근접 알림을 등록한 뒤 `adb emu geo fix`로 국립경주박물관 좌표를 주입하면 ENTER 전이가 수신되고, 모드는 폴백이 아니라 proximity로 바뀝니다. 이어진 파이프라인이 스탬프 1/3 기록과 다음 목표 대릉원 전환을 처리했고, 주행 화면에 "약 1.9km"가 표시됐습니다(개발 기록 F48·F49 — 스모크 U3).

**재진입 중복(AC04).** 대릉원 스탬프를 획득하고 첨성대 스탬프를 획득한 뒤 다시 대릉원 반경에 들어오면 도착 판정은 무효가 되고 추가 스탬프가 생기지 않습니다 — 단위 테스트 StampEngineTest `2_재진입 중복 방지_A획득후_B획득하고_다시_A에 도착하면 null이다`.

**연속 진행과 완주(AC06).** 국립경주박물관 도착(1/3)에 이어 대릉원 통과로 스탬프 2/3까지 자동 진행됐고(개발 기록 F74·F77), 3곳을 모두 찍은 뒤의 추가 도착 신호는 무효가 됩니다. 코스 완주 화면(스탬프 3/3)은 실측 화면 3·7(2026-11-11 캡처)로 남아 있고, 완주 뒤 감시 중단 동작은 단위 시험 TripSessionTest `4_모든 장소 도착시 완주_감시가 중단된다`로 확인했습니다(정본 AC06 note).

**주행 중 도착(AC07·AC08).** Virtual Console로 기어 D·시속 40km를 만든 상태에서 반경 안으로 들어가면 도착 판정·스탬프가 기록되고, 그동안 앱 화면은 시스템이 가립니다. 스탬프 등록 직후 다음 목적지(대릉원)의 경로 요청이 내비게이션 애플리케이션에 접수됐습니다. 경로 요청 접수까지는 확인했지만 길 안내 화면 표시 자체는 미확인입니다(개발 기록 F68 — 정본 AC08 note).

## 6. 오류·예외 처리

- 근접 알림 등록이 실패하거나 오류가 나면 FusedArrivalDetector가 폴백으로 전환해 위치 콜백 좌표로 거리를 직접 계산합니다(haversineActive 분기). "거리 ≤ 반경이면 도착"이라는 경계 판정은 엔진이 아니라 호출자가 합니다 — 소스 app/src/main/java/app/arosaegim/pleos/FusedArrivalDetector.kt, 단위 테스트 StampEngineTest `호출자 경계 판정_거리가 반경 이내여야만 엔진에 전달된다`, HaversineTest(거리 계산 단위 테스트). 정본 note에 따르면 실측에서는 근접 알림이 실패하지 않아 이 전환 장면 자체는 관찰되지 않았습니다(AC02 — 미확인).
- 네트워크가 없어 전송이 실패하면 방문 기록은 차 안 전송 대기열에 남고 나중에 다시 시도됩니다 — 단위 테스트 TripSessionTest `6_visitQueue_주입시 도착하면 큐에 1건 적재되고 전송을 시도한다`, 대기열 유지·재전송 세부는 [F9 문서](F9_오프라인대체구현.md) 6절.
- 가족 세션이 없는 앱의 방문은 전송이 401로 보류되고 대기열에 남습니다. 서버 DB 대조에서 그 앱의 방문이 0건으로 확인돼 전송 보류가 설계대로 동작함이 대조됐습니다 — 개발 기록 F78.
- 근접 알림 등록이 끝나기 전에 차가 이미 반경 안에 있으면 ENTER가 발화하지 않는 실측 사례가 있습니다. 코스는 반경 밖에서 시작해야 합니다 — 개발 기록 F68의 주의 문단(첫 시도 실패 원인).
- 내비게이션의 도착 콜백(onDestinationArrived)은 장소 식별자가 없고 실측에서 미발생이 관찰됐습니다. 그래서 이 콜백은 도착 판정에 쓰지 않고, 본역을 근접 알림으로 만들었습니다 — 개발 기록 F8(SDK AAR 확인)·F57(스모크 U10 관찰).

## 7. 시험·실측 연결

**단위 시험** (android/app/src/test)
- StampEngineTest — 첫 도착·재진입 중복·순서 위반·완주·reset·호출자 경계 판정.
- TripSessionTest — 첫 목표 도착 파이프라인·재도착 무시·순서 위반 무시·완주 감시 중단·reset·대기열 적재·경로 요청·재시작 복원.
- HaversineTest — 장소 간 거리 범위(국립경주박물관~대릉원 1.4~1.9km).

**에뮬레이터 실측** (docs/DEV_LOG.md U표·개발 기록)
- F48 — 근접 알림 ENTER 수신·반경 단위 미터 확정(스모크 U3).
