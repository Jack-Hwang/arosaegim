# F8 로컬 맛집·숙소 포인트 캐시백

## 1. 한눈에 보기

영수증(사진·금액·결제일·제휴처)을 규칙으로 판정해 포인트를 적립하는 기능입니다.
적립은 결제액의 1~2%(소수점 이하 버림)이고, 방문 연계(맛집·가게는 당일+다음 날, 숙소는 체크인~체크아웃 사이·최대 3박), 사진 필수, 같은 사진 재제출 거부, 같은 제휴처 같은 날 두 번째는 확인 대기(pending), 하루 5건 한도, 금액 상한(100만 원 포함 인정)이 규칙입니다.
판정 로직은 서버의 순수 함수이고 정본이 참조하는 10개 서버 시험이 전부 검증합니다. 전부 시뮬레이션이며 화면에는 '포인트 캐시백(예시)'과 '현금이 아니다'라는 말이 함께 나옵니다.
수용 기준 14건 중 [코드 확인] 10·(설계) 4입니다.
아직 미확인인 것: 영수증 화면(웹 화면 7) 단독의 실측 기록이 없고, (설계) 4건(AC11~AC14)은 코드 근거만 있습니다.

## 2. 목적과 범위

| 요소 | 내용 |
|---|---|
| 포함 | 점수 판정(방문 연계→중복→한도 조건 통과 시 floor(금액 × 적립률)), 맛집·가게 연계(스탬프 당일+다음 날), 숙소 연계(체크인~체크아웃 사이 스탬프·최대 3박·기간 밖·3박 초과·날짜 누락 거부), 사진 필수(400 missing_photo), 같은 사진(바이트 동일) 재제출 거부(duplicate_photo — 사진 해시는 원본 바이트 SHA-256), pending 저장(적립 0), 금액 경계(0원 이하·100만 원 초과 거부·100만 원 포함 인정), 하루 accepted 5건 한도(daily_limit), 포인트 합계 조회(단순 합), 숙소 선택 시 입력칸 전환(모바일 웹), 차량 화면 입력 없음, '포인트 캐시백(예시)'·'현금이 아니다' 문구 |
| 제외 | 실제 제휴 계약·적립 재원·정산·법규 검토(시뮬레이션 범위 밖), 사진 크기 상한의 별도 AC(정본 AC 범위에서 제외 — photos.py의 MAX_PHOTO_BYTES는 남아 있음), 구성원별 가중치·비교 계산(두지 않음 — AC11 note), 추첨·확률형 보상(없음) |
| 가정 | 적립률은 제휴처별 고정값(1%·2%)이고 확률·랜덤이 없습니다(docs/ARCHITECTURE.md 7절·9절 Q17). 가족의 합계는 구성원별 가중치 없이 단순 합입니다 — 누가 더 많이 벌었는지 비교하는 수단으로 쓰지 않기 위함입니다(AC11 note) |
| 경계 | 영수증 인증은 스마트폰 화면에서만 하고 차량 화면에는 금액·사진 입력칸이 없습니다(AC13). 방문 연계 장소가 정의되지 않은 제휴처는 no_visit이 아니라 정상 판정 경로로 통과합니다(AC03 참조 시험 test_wrong_partner_place_has_no_visit). 동의 화면은 '예시'만 적고 '현금이 아니다' 말은 없습니다(AC14 note) |

## 3. 입력·출력·상태

| 구분 | 항목 | 내용 |
|---|---|---|
| 입력 | 영수증 | 사진(필수)·금액·결제일·제휴처·숙박 날짜(체크인·체크아웃 — 숙소인 경우) |
| 입력 | 연계 정보 | 제휴처의 방문 연계 장소(near_place_id — 있을 때만 연계 검사) |
| 출력 | 판정 응답 | accepted(적립) / pending(확인 대기·적립 0) / rejected(사유 — invalid_amount·no_visit·duplicate_photo·daily_limit) |
| 출력 | 오류 응답 | 400(missing_photo·invalid_stay) |
| 출력 | 라벨 | '포인트 캐시백(예시)' 응답 라벨(AC01 io)과 화면 문구(AC14) |
| 출력 | 조회 | 가족의 포인트 합계(SUM(points), 가족 코드 단위 — AC11) |
| 상태 | 원장·키 | point_ledger(accepted 기록), receipt_key(제휴처+날짜+금액+사진 해시), 하루 accepted 카운트(5건 한도) |
| 상태 | 사진 | 사진 해시는 원본 바이트의 SHA-256 — 같은 바이트 재제출은 금액을 바꿔도 거부됩니다(AC07) |

## 5. 입력→출력 예시

**적립 계산(AC01·AC09).** 맛집 제휴처(적립률 2%)에 50,000원 영수증(사진 포함·방문 연계 통과)을 제출하면 accepted·1,000점(50,000×0.02)이 적립되고 응답 라벨은 '포인트 캐시백(예시)'입니다. 결제액 1,000,000원은 상한 안에 포함돼 accepted·20,000점이고, 1,000,001원·0원·-100원은 모두 rejected invalid_amount입니다 — 서버 시험 test_accepted_points_are_floored, test_amount_boundary.

**방문 연계(AC02·AC03·AC04·AC05).** 맛집은 스탬프 당일·다음 날 결제면 인정되고 이틀 뒤부터는 rejected no_visit입니다. 숙소는 기간 안 스탬프면 인정되고(체크아웃일 결제 포함), 기간 밖 스탬프는 no_visit, 4박 입력은 400 invalid_stay입니다 — 서버 시험 test_restaurant_same_day_accepted 등 네 케이스, test_lodging_within_stay_accepted 등 세 케이스.

**사진과 중복(AC06·AC07·AC08).** 사진 없는 제출은 400 missing_photo입니다. 사진 A로 제출한 뒤 같은 사진 A로 금액을 바꿔 재제출하면 rejected duplicate_photo입니다. 같은 제휴처·같은 날 두 번째는 pending(적립 0점·사진과 기록은 저장)이며, 다른 제휴처의 그날 첫 제출은 정상 적립됩니다 — 서버 시험 test_receipt_without_photo_rejected_400, test_same_photo_resubmission_rejected, test_second_receipt_same_partner_same_day_pending.

**한도(AC10).** 같은 날 다섯 제휴처에서 각각 첫 영수증이 accepted인 상태에서 여섯 번째(그날 처음인 제휴처)를 제출하면 rejected daily_limit입니다 — 서버 시험 test_daily_limit_after_five, test_evaluate_receipt_pure_function.

## 6. 오류·예외 처리

- 판정 순서(금액→중복→방문→대기→한도)는 evaluate_receipt 한 곳에 고정돼 있어 사유가 겹칠 때 결과가 흔들리지 않습니다 — docs/ADR.md ADR-011, 소스 backend/app/services/points.py(규칙 1~6).
- 사진 해시는 원본 바이트의 SHA-256입니다. 해시 기준을 응답이 아니라 원본 바이트로 두는 것을 서버 시험이 검증합니다 — 서버 시험 test_photo_hash_is_sha256_of_raw_bytes, test_receipt_key_uses_photo_hash.
- 숙박일수·날짜 누락의 거부는 서버 라우터의 숙박 기간 검증 코드와 서버 시험 3케이스(test_lodging_outside_stay_rejected·test_lodging_over_three_nights_rejected_400·test_lodging_missing_stay_dates_400)로 검증됩니다 — 소스 backend/app/config.py(MAX_STAY_NIGHTS=3).
- 포인트 합계 조회는 가족 코드 단위의 SUM(points)이며 구성원별 비교·나누기 계산을 두지 않습니다 — 소스 backend/app/routers/points.py(합계 조회 SQL), AC11 note(가족 관계를 겨루는 수단으로 쓰지 않기 위함).
- 문구 규칙은 코드 전수 검색으로 확인했습니다 — 차량 화면 1곳·스마트폰 화면 3곳에서 '포인트 캐시백(예시)'과 '현금이 아니다'가 함께 나오고, 동의 화면은 '예시'만 적습니다(AC14 note — 소스 web/js/screens/receipt.js 등).
