# 품질 게이트와 수치 기준

이 문서는 제출 기획서(접수양식)의 별지와 같은 표·같은 문장입니다(커밋 ba96030 기준). 글에 나오는 "본문 N번"·"별지 ○○"은 그 기획서를 가리킵니다. 숫자는 코드에서 센 값이며 코드가 바뀌면 `tools/spec_drift_check.py` 로 다시 대조합니다.


## 1. 비기능 요구 수치 게이트

> **한눈에 보기**
> '빠르게·안전하게' 같은 형용사 대신 직접 잴 수 있는 숫자 13개를 모아 기준·측정 방법·현재 값·상태를 한 표에 묶었습니다. 아홉 개는 코드·단위 시험으로, 두 개는 에뮬레이터에서 실제로 호출해 [확인]했고, 한 개는 공식 디자인 가이드 문서와 코드 적용 값을 대조해 [가이드 확인]했으며, 아직 목표 수치조차 정하지 않은 한 개는 (계획)으로 남겼습니다.
> 도착 판정 반경은 120m 진입 시 작동을 확인했지만, '반경 밖에서는 반응하지 않습니다'만 따로 재는 전용 경계 시험은 아직 없습니다 — 숨기지 않고 아래 표의 비고에 그대로 적었습니다.

비기능 요구(성능·신뢰성·보안 같은 '어떻게'에 대한 요구)는 '빠르다'처럼 느낌으로 쓰면 아무도 통과·불합격을 가릴 수 없습니다.

아래 표는 각 항목에 숫자 기준을 먼저 정하고, 그 숫자를 무엇으로 재는지(단위 시험 이름, 에뮬레이터 호출, 코드 구조 점검)까지 밝혀, 다른 사람이 같은 방법으로 다시 재도 같은 값이 나오게 했습니다.

**비기능·보안·신뢰성 수치 게이트 13개**

## 2. Well-Architected 5기둥 — 로컬·오프라인 맥락으로 다시 쓰기

> **한눈에 보기**
> 클라우드 서비스를 가정한 품질 다섯 기둥(신뢰성·보안·비용·운영 우수성·성능 효율성)을, 혼자 개발하고 서버 없이도 핵심 기능이 돌아가는 이 앱의 조건으로 다시 썼습니다.
> 자동 확장·여러 지역 배포 같은 클라우드 전용 항목은 이 앱에 해당하지 않아 애초에 질문에서 뺐습니다. 성능 효율성은 아직 목표 수치가 없어 '충족'이라고 단정하지 않았습니다.

**Well-Architected 5기둥을 아로새김의 질문으로 다시 쓴 결과**

| 기둥 | 이 앱의 질문 | 답 |
|---|---|---|
| 신뢰성 | 서버 연결이 끊기거나 차량 신호가 늦게 와도 핵심 흐름(도착→스탬프→퀴즈)이 멈추지 않는가 | 차량 신호는 정식·대체 구현을 둘씩 둔 7개 포트 뒤로 감쌌고(설계 결정 ADR-001·ADR-014), 방문 기록은 전송 대기열에 먼저 쌓였다가 연결이 돌아오면 다시 보냅니다. 코드 입력부터 서버 기록까지 전 구간을 한 번에 재실측하는 일만 아직 남아 있습니다. |
| 보안 | 가족이 아닌 사람이 위치·차대번호·아동 사진 같은 민감한 정보를 보거나 바꿀 수 있는가 | 좌표는 애초에 저장하지 않고, 차대번호는 지원 여부만 확인하며 값을 읽지 않습니다. 미성년 구성원이 있는 가족은 보호자 동의 없이 사진을 올리면 서버가 거부합니다(아래 3절 표). |
| 비용 | 포인트 캐시백을 한도 없이 주어 '만든 돈'(가정 지급액)이 걷잡을 수 없이 커지는가 | 영수증 1건당 100만 원 이하, 가족 1곳 하루 5건까지만 인정해(ADR-011) 가정 지급액의 위쪽 한계를 코드로 고정했습니다. 포인트 캐시백과 관련된 모든 화면에 '시뮬레이션'이라는 말과 현금이 아니라는 말을 함께 둡니다. |
| 운영 우수성 | 혼자 개발하는 상황에서 빌드·점검을 다른 사람도 같은 결과로 되풀이할 수 있는가 | 시험과 빌드는 명령 한 줄로 재현할 수 있고, 문서에 적은 숫자(테스트 수·용량 등)가 코드와 어긋나면 자동으로 잡아내는 도구를 저장소에 두었습니다(6절 출시 게이트). |
| 성능 효율성 | 주행 중 반응(스탬프 인식·퀴즈 로딩)이 안전을 해치지 않을 만큼 빠른가 | 아직 구체적인 목표 시간이나 실측값이 없습니다(계획, 측정 전). 2차 발표 전 에뮬레이터로 체감 지연을 재어 볼 과제로 남아 있습니다. |

*클라우드 기둥 문항(자동 확장·다중 지역 장애 대비 등)은 서버 1대·앱 1종 구조에 맞지 않아 그대로 옮기지 않고, 이 앱 규모에 맞는 질문으로 바꿔 썼습니다.*


## 3. 안전·개인정보 위협과 오남용 시나리오

> **한눈에 보기**
> 가족 코드·PIN·위치·차대번호·아동 사진·영수증처럼 민감하거나 오남용될 수 있는 자리마다 '무슨 일이 생길 수 있는가'를 먼저 적고, 그것을 막는 수단과 근거를 나란히 적었습니다.
> 여덟 가지 가운데 여섯은 코드로 막는 수단이 이미 있고 단위 시험으로 확인됩니다. 가족 코드를 무작위로 맞히는 시도에 대한 요청 빈도 제한과, 로그아웃을 누르지 않고 차를 넘기는 상황에 대한 자동 장치는 코드에서 찾지 못했습니다 — 그대로 밝힙니다.

**안전·개인정보 위협과 오남용 시나리오 8가지**

| 시나리오 | 무슨 일이 생길 수 있는가 | 막는 수단과 확인 | 상태 |
|---|---|---|---|
| 가족 코드 추측 | 코드를 무작위로 맞혀 그 가족의 방문 기록·사진을 들여다봄 | 코드는 헷갈리는 글자를 뺀 31개 문자 중 8자리 조합(약 8,529억 가지, 가정 계산: 31의 8제곱)입니다. 다만 같은 코드를 계속 시도하는 것을 따로 막는 요청 빈도 제한은 코드에서 찾지 못했습니다. | [일부 확인] |
| 가족 코드 공유(의도치 않은 유출 포함) | 코드를 알게 된 사람이 가족인 척 기록을 추가·변경함 | 코드만으로는 '그때와 지금'·스탬프북 같은 읽기 일부만 되고, 기록을 더하거나 바꾸는 쓰기 작업은 모두 별도 PIN이 있어야 합니다(설계 결정 ADR-010). | [코드 확인] |
| PIN 오남용(무차별 대입) | 코드를 아는 사람이 PIN을 여러 번 틀리게 넣어 맞히려 함 | 5회 연속 틀리면 그 가족의 모든 요청을 10분간 막습니다(수용 기준 ARO-F7-AC03). PIN을 아는 사람이라면 코드 재발급으로 즉시 풀 수 있습니다(5절 1번). | [코드 확인] |
| 위치(이동 경로) 유출 | 차가 지나온 경로가 새어 나가 가족의 평소 동선이 드러남 | 좌표를 아예 저장하지 않습니다 — 로컬 방문 기록 자료 구조에 좌표를 담는 자리 자체가 없습니다. | [코드 확인] |
| 차대번호(VIN) 유출 | 차량 고유 번호가 기록·전송되어 특정 차량과 사람을 연결 지을 단서가 됨 | 번호를 읽는 기능이 지원되는지 여부만 확인하고, 번호 값 자체는 호출하지 않습니다. | [코드 확인] |
| 아동 사진 유출·오남용 | 보호자 동의 없이 미성년 구성원의 사진이 서버에 쌓임 | 미성년 구성원이 있는데 보호자 동의가 없으면 사진이 딸린 기억 기록 저장을 거부합니다(수용 기준 ARO-F7-AC08). | [코드 확인] |
| 로그아웃 없이 차 돌려주기 | 다음 사람(대여·공유·가족 외)이 이전 가족의 코드·기록을 그대로 이어받음 | '이 차에서 로그아웃'을 실행하면 코드·PIN·방문 기록·전송 대기열을 모두 지웁니다(수용 기준 ARO-F6-AC10). 다만 이 실행 버튼은 지금 개발용 진단 화면에만 있어 일반 사용자가 쓰는 화면에는 아직 없고, 자동으로 지우는 시간제 장치도 찾지 못했습니다. | [일부 확인] |
| 영수증 중복 제출 | 같은 영수증(사진)으로 포인트 캐시백을 여러 번 받으려 함 | 제휴처·날짜·금액에 사진 해시값까지 더한 값으로 중복을 가려내, 같은 조합이나 같은 사진의 재제출은 다시 적립되지 않습니다. | [코드 확인] |

*'일부 확인'은 핵심 방어 수단은 있지만 한 자락(요청 빈도 제한, 일반 사용자가 쓸 수 있는 로그아웃 화면, 자동 로그아웃)이 비어 있다는 뜻입니다 — 사용자가 정할 일로 남겨 '가정과 열린 질문 로그'에 함께 올립니다.*


## 4. 쓰기 행동 전수 목록

> **한눈에 보기**
> 앱과 서버가 상태를 바꾸는 행동을 전부 모았습니다. 차량 쪽은 5갈래(로그인·PIN 보관·방문 기록·전송 대기열·로그아웃), 서버 쪽은 API 묶음별로 6갈래입니다.
> 모든 쓰기 행동에는 적어도 하나의 가드(검사·한도·인증)가 걸려 있습니다. 가드가 없는 쓰기 행동은 찾지 못했습니다.

**상태를 바꾸는 쓰기 행동 전수와 가드**

| 쓰기 행동 | 저장 위치·방식 | 가드(검사·한도·인증) |
|---|---|---|
| 가족 코드 로그인·둘러보기 전환 | 차량 쪽 기기 설정값 한 칸(코드만, PIN은 제외) | 코드가 영문·숫자 6~8자리인지 먼저 검사하고, 공백·특수문자·한글이 섞이면 받아들이지 않습니다 |
| PIN 세션 보관·해제 | 차량 쪽 프로세스 메모리뿐(기기 설정값·파일에는 남기지 않음) | 앱을 다시 켜면 사라져 다시 넣어야 합니다(설계 결정 ADR-003) |
| 방문(스탬프) 기록 | 차량 쪽 파일 1개 + 서버에 전송 | 도착 처리 순서 고정(ADR-002), 같은 장소·코스·분(1분 단위)·가족이면 새로 만들지 않고 기존 기록을 그대로 씀(ADR-004) |
| 전송 대기열 적재·정리 | 차량 쪽 파일 1개 | 같은 멱등 키 규칙을 적용하고, 로그아웃 시 함께 지움 |
| 이 차에서 로그아웃 | 차량 쪽 코드·PIN·방문 기록·전송 대기열 삭제 | 삭제 결과를 한 줄씩 남기고, 한 파일이 실패해도 나머지 삭제를 멈추지 않음(단위 시험 4건) |
| 가족 발급·탈퇴·코드 재발급 | 서버 가족 표(새 코드 발급, 탈퇴 시 전량 삭제) | 탈퇴·재발급은 PIN이 있어야 하고, 탈퇴는 업로드한 사진 파일까지 함께 지움 |
| 구성원 추가·좌석 역할·보호자 동의 기록 | 서버 구성원 표 | 코드+PIN 인증이 필요하고, 보호자 동의 기록은 한 번 남기면 되돌릴 수 없음(삭제 없음) |
| 이어받을 사람 지정·물려주기 | 서버 가족 표의 이어받을 사람 칸 | 보호자(소유자) 자격을 PIN으로 확인해, 틀리면 거부(인증 안 됨과 권한 없음을 구분해 응답) |
| 사진·기억 업로드·사진 속 이름표 | 서버 기억 표 + 업로드 파일 | 코드+PIN 인증, 미성년 구성원이 있는데 보호자 동의가 없으면 사진이 딸린 기록은 거부 |
| 영수증 제출(포인트 캐시백 판정) | 서버 영수증 표 + 포인트 합계 | 사진 필수, 사진 해시를 포함한 값으로 중복 검사, 건당·하루 한도 검사(ADR-011) |
| 설정·장소 접어 두기·인원 비교 선호 저장 | 서버 가족 설정 표(차량 쪽은 서버 응답 전 임시 보관) | 코드+PIN 인증, 접기는 장소별로 켜고 끌 수 있을 뿐 기록 자체를 지우지는 않음 |

*묶음 안의 여러 주소(예: 구성원 추가·좌석 역할·동의)는 모두 같은 인증 방식을 쓰므로 한 줄로 묶었습니다 — 실제로는 서버 쪽에서만 열일곱 개 안팎의 개별 요청 주소가 있습니다.*


## 5. 과잉 차단 방지 점검

> **한눈에 보기**
> 안전·보안 장치가 정상적인 사용까지 막아 버리는 일(과잉 차단)이 없는지 네 곳을 짚었습니다. 그 가운데 하나(릴리스 통신 차단)는 실제로 있었던 과잉 차단이고 고쳤으며, 나머지 세 곳은 애초에 범위를 좁혀 설계해 과잉 차단을 피했습니다.

**안전장치가 정상 기능까지 막지 않도록 한 설계**

| 안전장치 | 정상 기능을 막을 수 있었던 지점 | 막지 않도록 한 설계 |
|---|---|---|
| 릴리스 빌드의 평문 통신 차단(보안 강화) | 서버 호출 전체가 막혀 가족 코드 이어 보기·'그때와 지금' 조회·방문 기록 전송까지 조용히 실패 | 실제로 이 과잉 차단이 있었던 것을 찾아, 허용 대상을 시험 서버 주소로만 좁혀 되돌렸습니다. 운영 환경에서는 암호화 통신 요구를 그대로 유지합니다(개발 기록 F71) |
| 가족 PIN 5회 잠금(10분) | PIN을 정확히 아는 가족까지 10분을 꼼짝없이 기다려야 함 | 코드를 재발급하면(코드+PIN 모두 새로 받음) 잠금 중에도 즉시 풀립니다(수용 기준 ARO-F7-AC04). PIN을 모르는 사람은 이 경로로도 아무것도 얻지 못합니다 |
| 미성년 구성원 보호자 동의 요구 | 동의를 아직 못 받았다는 이유로 그 가족의 모든 기록 저장을 막아 버릴 위험 | 막는 범위를 '사진이 딸린' 기억 기록으로 좁혔습니다 — 사진 없는 글 기록은 동의 여부와 무관하게 그대로 저장됩니다(수용 기준 ARO-F7-AC09) |
| 주행 중 화면 전환 제한(안전) | 정차 중에도 지나치게 넓게 막아 퀴즈 응답·스탬프 확인 같은 정상 동작까지 가릴 위험 | 자동 전환을 막는 조건은 '정차 화면으로 넘어가는 순간'에만 걸려 있고(설계 결정 ADR-006), 이미 정차 화면에 들어간 뒤의 퀴즈 응답·스탬프 확인 자체는 이 조건의 대상이 아닙니다 |


## 6. 출시 게이트 — 사람이 아니라 기계가 판정하는 기준

> **한눈에 보기**
> '다 됐다'는 사람의 느낌이 아니라 명령 하나의 성공·실패로 판정하는 활동 여섯 가지와, 사람이 직접 확인해야 하는 활동 두 가지를 나눠 적었습니다. 지금까지는 1~6번 모두 통과한 상태입니다.

**출시 전 거쳐야 할 게이트 8가지**

| 활동 | 산출물 | 기계 판정 기준 | 비고 |
|---|---|---|---|
| 앱 단위 테스트 실행 | 테스트 결과 집계 | 271/271 통과(실패 0건) | 기계 판정 |
| 서버 단위 테스트 실행 | 테스트 결과 집계 | 137/137 통과(실패 0건) | 기계 판정 |
| 앱 디버그 빌드 | 디버그용 설치 파일 | 빌드 성공(실패 종료 코드 없음) | 기계 판정 |
| 앱 릴리스 빌드·서명 | 서명된 릴리스 설치 파일 | 빌드 성공 + 파일이 실제로 만들어지고 용량이 기록값과 같음(40,652,561바이트) | 기계 판정 |
| 서버 상태 확인 | 상태 확인 응답 | 정상 200 응답을 돌려줌 | 기계 판정 |
| 문서 숫자 자동 대조 | 대조 결과(문서와 코드가 다른 곳 목록) | 불일치 0건 | 기계 판정(저장소의 자동 대조 도구) |
| 설치·스탬프 실측(최종 점검) | 에뮬레이터 실측 캡처 | 설치 성공 + 스탬프 1건 이상 기록 확인 | 사람 확인 |
| 접수 서류 제출 | 접수 메일 | 저장소 주소와 이 별지가 근거로 삼은 최종 커밋 번호를 적었는지 | 사람 확인(7절 체크리스트) |

*'기계 판정'은 사람이 결과를 눈으로 해석할 필요 없이 명령의 성공·실패 자체가 통과·불합격을 가른다는 뜻이고, '사람 확인'은 기계가 대신 봐 줄 수 없는 마지막 확인입니다.*


## 7. 설계 리뷰 자체 점검과 제출 전 체크리스트

> **한눈에 보기**
> 제출 직전에 스스로 점검하는 다섯 가지 물음(비례성·결정적 강제·근본 원인·불확실성 보존·산출물 저장)을 이 고도화 작업 전체에 적용한 결과입니다. 네 가지는 충족, 한 가지('산출물 저장')는 저장소 문서 사이의 작은 어긋남 때문에 '일부 충족'입니다.
> 뒤이어 제출 직전 사람이 직접 할 일 두 가지를 포함한 체크리스트를 둡니다.

**설계 리뷰 5가지 물음 자체 점검**

| 물음 | 점검 내용 | 이번 고도화에 적용한 결과 | 판정 |
|---|---|---|---|
| 비례성 | 마감까지 가능한 크기로 범위를 잡았는가 | 꼭 필요한 범위(필수·이후 범위·하지 않는 것)를 정리한 틀을 그대로 따르고, 이 별지도 코드에서 직접 잴 수 있는 사실만 더했습니다 | 충족 |
| 결정적 강제 | 지켜야 할 규칙이 사람의 주의가 아니라 코드로 강제되는가 | PIN 잠금·포인트 캐시백 상한·보호자 동의 거부는 모두 서버가 조건을 검사해 거부하는 코드이고, 그 결과가 단위 시험으로 고정돼 있습니다 | 충족 |
| 근본 원인 | 증상만 가리지 않고 원인까지 고쳤는가 | 릴리스 빌드의 통신 차단 사례(5절 1번)는 증상(요청 실패)이 아니라 원인(네트워크 보안 설정)을 찾아 고쳤습니다 | 충족 |
| 불확실성 보존 | 아직 모르는 것을 안다고 쓰지 않았는가 | 반경 밖 무반응의 전용 경계 시험, 차량 체감 지연 목표, 로그아웃을 누르지 않았을 때의 자동 장치 여부를 (계획)·[일부 확인]으로 그대로 남겼습니다 | 충족 |
| 산출물 저장 | 결정과 근거를 나중에도 찾아볼 수 있는 곳에 남겼는가 | 설계 결정 14건과 요구-구현-시험 대조표가 저장소 문서에 코드와 함께 있습니다. 대조표와 문서들의 최신 테스트 수치(197·87) 동기화는 코드 동결 시점에 최종 확인한다 | 일부 충족 |


### 제출 전 체크리스트

- **기계 확인**: 앱 단위 테스트 271/271, 서버 단위 테스트 137/137, 디버그·릴리스 빌드 모두 성공(6절 표).
- **기계 확인**: 문서 숫자 자동 대조 도구를 돌려 불일치 0건을 확인합니다(6절 표).
- **사람 확인**: 설치 후 에뮬레이터에서 스탬프 1건 이상이 실제로 찍히는지 마지막으로 눈으로 봅니다.
- **사람 확인(사용자 몫)**: 본문의 '기획 배경'과 '주요 사용 시나리오' 항목을 최신본으로 마지막까지 읽어, 이 별지들의 사실과 어긋나는 곳이 없는지 확인합니다.
- **사람 확인(사용자 몫)**: 접수 메일 본문에 저장소 주소와 이 별지들이 근거로 삼은 최종 커밋 번호(지금 기준 ba96030, 그 뒤 더 새 커밋이 있으면 그 번호)를 함께 적습니다.
- 체크리스트의 어느 한 줄이라도 아니오이면, 그 줄을 고치기 전에는 제출하지 않습니다 — 분량을 채우는 것보다 이 다섯 가지 물음과 수치 게이트가 실제로 통과하는 것이 먼저입니다.
