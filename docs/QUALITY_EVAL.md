# 평가 지표 적용표와 품질 스코어카드

이 문서는 제출 기획서(접수양식)의 별지와 같은 표·같은 문장입니다(커밋 ba96030 기준). 글에 나오는 "본문 N번"·"별지 ○○"은 그 기획서를 가리킵니다. 숫자는 코드에서 센 값이며 코드가 바뀌면 `tools/spec_drift_check.py` 로 다시 대조합니다.


## 1. 평가 체계를 아로새김에 맞춰 적용하는 법

> **한눈에 보기**
> 인공지능 서비스의 품질을 재는 틀을 빌려 와, 정답이 있는 항목과 없는 항목을 나누고 누가 채점하는지·언제 재는지를 먼저 정리합니다.
> 그다음 골든셋(미리 모아 둔 정답 문제집)부터 환류까지 여섯 단계를 아로새김의 실제 결과(앱 단위 시험 179건, 서버 시험 87건)로 채웠습니다.
> 아로새김은 앱 안에서 생성형 인공지능을 쓰지 않으므로, 다른 인공지능 모델이 채점하는 방식은 쓰지 않습니다 (2절에서 항목별로 밝힙니다).

품질을 재는 지표는 성격이 서로 다릅니다. 이를 가르는 세 가지 기준(축)을 먼저 정리하면, 아로새김의 어느 기능에 어떤 방식의 점검이 맞는지 고를 수 있습니다.

**평가 지표를 가르는 세 가지 기준**

| 기준(축) | 두 갈래 | 아로새김에서의 뜻 |
|---|---|---|
| 정답 필요 여부 | 정답이 있어 맞고 틀림을 가릴 수 있는 것 ↔ 정답이 없어 규칙 위반 여부만 보는 것 | 퀴즈 채점·연도 계산·포인트 캐시백 금액 계산은 정답이 있습니다. 개인정보·주행 중 입력 제한은 '위반이 있었는가'만 봅니다. |
| 채점자 | 미리 정한 규칙(코드) · 사람 · 다른 인공지능 모델 | 아로새김은 규칙과 사람만 씁니다. 앱 안에 생성형 인공지능이 없어, 다른 모델이 채점하는 방식(2절 8행)은 쓰지 않습니다. |
| 시점 | 만들기 전에 미리 모아 둔 문제로 재는 것(오프라인) ↔ 실제로 쓰는 중에 계속 관찰하는 것(온라인) | 지금은 전부 출시 전 점검(오프라인)입니다. 실제 사용 데이터를 보는 운영 중 관찰은 2차 발표 이후 과제로 남습니다. |


### 공통 평가 순서 — 골든셋부터 환류까지

품질을 재는 절차는 보통 여섯 단계로 돕니다: 미리 정답을 모아 두고(골든셋) → 앱이 실제로 값을 만들고(실행) → 정답과 맞춰 보고(채점) → 건수를 더하고(집계) → 기준에 못 미치면 반영을 멈추고(게이트) → 그 결과를 다음 수정에 되먹입니다(환류).

아로새김에 이미 있는 증거로 이 여섯 단계를 하나씩 채웠습니다.

- **골든셋**: 퀴즈 6문항(장소 3곳 × 2문항, 정답 번호·해설이 미리 정해짐), '그때와 지금' 연도 차이 계산 단위 시험 12건, 포인트 캐시백 판정 시험 9건(금액 상한 경계값 포함) — 전부 입력과 기대 결과가 쌍으로 코드에 이미 있습니다.
- **실행**: 고른 보기 번호를 코드가 그대로 비교하거나, 연도·금액을 정해진 계산식에 넣어 값을 만듭니다 (소스 코드).
- **채점**: 미리 정한 값과 완전히 같은지만 봅니다(사람 말로 '정확히 맞았는가'를 보는 채점 방식 — 다섯 글자 '완전 일치'). 비슷한 말을 맞게 보는 채점은 쓰지 않습니다.
- **집계**: 통과한 시험 건수를 더합니다. 지금 값은 앱 단위 시험 179건·서버 시험 87건 전부 통과입니다 (개발 기록 F81·F82·F85, 2026-11-13 오후 기준).
- **게이트**: 하나라도 실패하면 그 수정은 반영하지 않습니다. 문서 숫자도 같은 성격의 기준을 둡니다(5절).
- **환류**: 실패나 미해결 질문은 개발 기록의 번호(F·Q)로 남겨 다음 수정의 출발점이 됩니다. 기어 P 보류 해제 규칙(설계 결정 ADR-005)이 그렇게 나온 예입니다.


## 2. 평가 지표 10종 적용표

> **한눈에 보기**
> 인공지능 서비스에서 흔히 쓰는 지표 10가지를 하나씩 아로새김에 대 보았습니다. 앱 안에 생성형 인공지능이 없으므로 '다른 모델이 채점'하는 지표 하나는 해당 없음으로 분명히 적었습니다.
> 숫자가 있는 항목은 전부 단위 시험·서버 시험·에뮬레이터 실측 결과이며, 아직 실행하지 못한 점검은 (계획)으로 구분했습니다. 근거 검색 프로그램 자체의 검색 점수는 앱 기능이 아니라서 쓰지 않았습니다.

**평가 지표 10종의 아로새김 적용**

| 지표 | 아로새김 대응 대상·방법 | 현재 값 | 목표 | 상태 |
|---|---|---|---|---|
| ① 정답도 | 퀴즈 채점·'그때와 지금' 연도 계산·포인트 캐시백 금액 계산. 미리 정한 값과 완전히 같은지 비교(완전 일치)합니다. | 퀴즈 6문항 코드 확인, 연도 계산 12건·금액 판정 9건 시험 전부 통과 | 전부 통과 유지(회귀 게이트) | [코드 확인] |
| ② 근거성 | 해설 3건·유물 연도 3건·퀴즈 해설 6건의 역사적 주장을 문장 단위로 쪼개 공식 자료와 맞춰 봅니다. 자동 비교는 생성형 인공지능이 필요해 쓰지 않고 사람이 직접 맞춰 봅니다. | 12건 전부 검수 전(초안, reviewed=false) | 1차 제출 전 대조 틀 마련, 검수 완료는 과제로 공개 | (계획) |
| ③ 관련성·완결성 | 예상 질문·답변 문서의 답이 질문과 맞는지(관련성), 포인트 캐시백이 '현금이 아님'을 밝히는 문구가 관련 화면마다 빠짐없이 있는지(완결성)를 점검합니다. | 체크리스트 설계만 끝남, 실행 전 | 1차 제출 전 전 화면 1회 점검 | (계획) |
| ④ 검색 품질(축소) | 로컬 맛집·숙소는 검색엔진이 아니라 장소별로 미리 정해 둔 제휴처를 그대로 꺼내 옵니다. 적중률만 보고 순위 지표는 쓰지 않습니다. | 제휴처 4곳 전부 지정 장소에만 연결, 다른 장소로는 연결 안 됨 | 그대로 유지 | [코드 확인] |

| ⑥ 궤적·과제 완수 | 도착→정차→스탬프→퀴즈→'그때와 지금'→다음 목적지로 이어지는 코스 완주 흐름 전체를 목표 상태 목록으로 보고 점검합니다. | 완주 로직 코드 확인, 실측은 1번째→2번째 장소 전환까지 확인(3번째 장소 연속 실측은 미확인) | 2차 발표 전 3곳 전체 3회 반복 재현 | [일부 확인] |
| ⑦ 안전성 | 주행 중 입력 차단(주행 최적화)과 개인정보 세 가지(좌표 비저장·차대번호 미조회·PIN 메모리 보관)를 규칙 위반 0건 기준으로 봅니다. | 개인정보 세 가지 코드 확인, 주행 중 입력 전수 점검은 실행 전 | 전수 점검 위반 0건, 수정마다 재확인 | [일부 확인] |
| ⑧ 다른 모델의 채점(LLM 심사) | 다른 거대 언어 모델(LLM, 글을 만드는 대형 인공지능)이 결과를 채점하는 방식입니다. | 해당 없음 | 해당 없음 | 해당 없음(앱에 모델 심사기 없음) |
| ⑨ 사람 평가 | 검수자 자가 일관성 재점검과 가족·지인 소표본 선호 조사(4절에서 자세히) | 계획 단계, 실행 전 | 2차 발표 전 각 1회 | (계획) |
| ⑩ 회귀 게이트 | 코드를 고칠 때마다 전체 시험과 문서 숫자 대조를 다시 돌려 기준 미달이면 반영을 멈춥니다(6절). | 앱 179/179·서버 87/87 통과, 문서 숫자 9개 사실 대조(현재 커밋 기준) | 제출 직전 커밋까지 유지 | [코드 확인] |

*①~⑤·⑩은 규칙(코드)이 채점하고, ⑦은 규칙과 사람 점검이 함께, ⑨는 사람이 채점합니다. ⑧은 생성형 인공지능이 없어 아예 해당하지 않는 지표라 숨기지 않고 그대로 적었습니다.*


### 다섯 번째 지표의 실측 근거 — Pleos SDK 호출 결과 분포(U1~U16)

다섯 번째 지표(도구 호출 정확도)의 실측 값은 에뮬레이터에서 포트 7개의 실제 호출 결과를 16가지 항목으로 나눠 확인한 기록입니다. 모의 시험은 호출의 이름·인자·순서만 보고, 이 표는 실제 차량 신호 응답까지 봅니다.

**Pleos SDK 호출 결과 분포(U1~U16, 에뮬레이터 v2.1.0 실측)**

| 결과 | 건수 | 해당 항목(근거) |
|---|---|---|
| 성공(PASS) | 9 | U1 경로 요청 접수·U2 경로 부품 초기화·U3 근접 알림 ENTER 수신·U4 지원 여부 확인·U5 기어 상태 수신·U8 서버 연결·U9 화면 전환 3회·U13 주행거리계 수신·U16 전기차 배터리 지원 |
| 실패(FAIL) | 2 | U6 음성 합성(원인 2건 확정, 개발 기록 F54) · U15 연료 신호 지원(에뮬레이터가 연료 속성을 지원하지 않음, 개발 기록 F76) |
| 부분 확인 | 2 | U7 주행 규제 전환(세부 항목은 열린 질문으로 남음) · U11 좌석 점유(권한 누락을 찾아 고친 뒤 조회는 성공, 화면 문장 반영은 대기) |
| 관찰 중(설계대로) | 1 | U10 도착 이벤트 관찰 — 발생하지 않는 것이 설계된 정상 결과 |
| 해당 없음(사용 안 함) | 2 | U12 문 상태·U14 배터리(연료형) — 아로새김이 쓰지 않는 신호라 고정 안내만 표시 |

*실측은 에뮬레이터 1대에서 한 번씩 본 결과이며(개발 기록 F48·F49·F76), 실제 차량에서의 재실측은 아직입니다.*


## 3. 품질 간이 스코어카드와 기능 연결표

> **한눈에 보기**
> 10가지 지표를 다시 세 갈래(콘텐츠 신뢰성·안전·재현성)로 묶어 한 장으로 요약했습니다. 문서 자체의 숫자 정확성도 품질의 일부로 같은 표에 넣었습니다.
> 그 아래 표는 아로새김의 아홉 기능과 품질 보증 수단을 나란히 이어, 기능마다 무엇으로 신뢰를 보증하는지 한눈에 보이게 했습니다.

**품질 간이 스코어카드**

| 항목 | 현재 | 목표 | 상태 |
|---|---|---|---|
| 콘텐츠 신뢰성(정답도) | 퀴즈 6문항 채점 로직·연도 계산 12건·금액 판정 9건 시험 전부 통과 | 전부 통과 유지(회귀 게이트) | [코드 확인] |
| 콘텐츠 신뢰성(근거성) | 해설·유물 연도·퀴즈 해설 12건 전부 검수 전(초안) | 1차 제출 전 대조 틀 마련 | (계획) |
| 안전(개인정보) | 좌표 비저장·차대번호 미조회·PIN 메모리 보관 코드 확인 | 수정마다 재확인 | [코드 확인] |

| F7 가족 기록 서버·모바일 웹 | 안전성, 도구 호출 정확도(서버 계약 시험) |
| F8 로컬 맛집·숙소 포인트 캐시백 | 정답도(금액 계산), 관련성·완결성('현금 아님' 문구 점검) |
| F9 오프라인·대체 구현 | 도구 호출 정확도(포트 7개 계약 시험) |

*이 표는 새 기준을 만들지 않고, 2절 표와 기능별 수용 기준(F1~F9)을 이어 보여 줄 뿐입니다.*


## 4. 사람이 보는 품질 — 선호 조사와 검수자 재점검

> **한눈에 보기**
> 가족·지인에게 보여 주는 소표본 선호 조사와, 콘텐츠를 검수하는 사람 스스로의 일관성 재점검 두 가지를 계획 단계로 적었습니다.
> 둘 다 표본이 아주 작아 통계적으로 일반화할 수 없습니다 — 참고용이라고 분명히 밝히고, 1인이 검수하는 한계도 숨기지 않습니다.


### 가족·지인 소표본 선호 조사

- **누구에게**: 가족·지인 가운데 실제로 태워 볼 수 있는 몇 명(통계적 의미가 있는 표본이 아님을 미리 밝힙니다).
- **무엇을**: 고친 전후 화면(캡처 또는 실제 기기)을 나란히 보여 주고 어느 쪽이 더 낫게 느껴지는지 간단히 묻는 방식입니다.
- **쓰는 곳**: 사업·운영 보강 자료의 사용자 반응 근거로만 쓰고, '몇 퍼센트가 선호했다' 같은 통계 문장으로 확대하지 않습니다.
- **시점**: 2차 발표 전. 지금은 계획 단계이고 아직 실행하지 않았습니다.


### 검수자 자가 일관성 재점검

해설·퀴즈 검수는 지금 한 사람이 맡고 있어, 여러 사람이 매긴 점수가 서로 얼마나 같은지 보는 평가자간 일치도는 잴 수 없습니다. 이 한계를 숨기지 않고, 대신 같은 사람이 시간을 두고 같은 항목을 다시 보는 방법으로 대신합니다.

- 지금 검수 전(초안)으로 남아 있는 해설 3건·유물 연도 3건·퀴즈 해설 6건, 모두 12건을 재점검 대상으로 삼습니다.
- 1차 제출 뒤 시간(예: 일주일 이상)을 두고 같은 12건을 처음 볼 때처럼 다시 판정해, 전과 같은 판정이 나오는지 봅니다.
- '사람 사이의 일치도'가 아니라 '한 사람의 판정이 시간이 지나도 흔들리지 않는가'만 보는 좁은 점검이라는 점을 결과에 함께 적습니다.


## 5. 문서 숫자의 품질 보증 — 사실 대장과 자동 대조

> **한눈에 보기**
> 같은 숫자(시험 건수 등)를 여러 쪽에 손으로 베껴 쓰면 코드가 바뀐 뒤 서로 어긋나는 일이 실제로 있었습니다 (개발 기록).
> 그래서 숫자를 코드에서 직접 다시 세어 '사실 대장' 한 곳과 맞춰 보는 자동 점검을 둡니다 — 이 별지의 숫자도 같은 방식으로 다시 대조됩니다.

정본 규칙은 같은 숫자나 사실을 한 곳에만 적고 다른 절은 그 곳을 가리키는 것입니다. 이 규칙을 문서에서 말로만 지키라고 하면 다시 어긋나기 쉽습니다.

그래서 개발 기록(F85)에 따르면 구현 저장소의 도구 폴더에 숫자를 코드에서 직접 다시 세어 문서의 같은 문장과 맞춰 보는 프로그램과, 무엇을 어떻게 세는지 적어 둔 '사실 대장' 파일이 만들어졌습니다.

- **사실 대장에 등록된 9가지**: 앱 단위 시험 건수·서버 시험 건수·서버 엔드포인트 수·서버 라우터 수·모델 클래스 수·화면 문구 수·앱 시험 파일 수·서버 시험 파일 수·릴리스 설치 파일(APK) 크기.
- **세는 법**: 사람이 눈으로 세지 않고, 소스 코드에 실제로 적힌 표시(예: 단위 시험 표시 @Test, 서버 시험 함수 이름 def test_)의 개수를 코드 관리 도구로 직접 셉니다.
- **대조 결과**: 추적표 문서 4절에 적힌 대로, 직전 점검에서 9개 사실이 전부 일치했습니다(코드로 다시 센 값과 문서의 숫자가 같았습니다).
- **이 별지의 숫자도 포함**: 이 별지에 적은 앱 단위 시험 179건·서버 시험 87건 같은 숫자도 같은 사실 대장 기준으로 다시 대조됩니다. 접수 전 마지막 점검에서, 이 별지를 고친 뒤에도 9개 사실이 모두 일치해야 합니다.
- **쓰지 않은 지표**: 근거를 찾는 데 쓴 검색 프로그램 자체가 매기는 검색 점수는 앱의 기능이 아니고 코드가 바뀔 때마다 값이 달라지므로, 이 별지의 숫자로 쓰지 않았습니다.


## 6. 안전·회귀 게이트와 시연 대본 점검(2차 발표 대비)

> **한눈에 보기**
> 코드를 고칠 때마다 전체 시험과 문서 숫자 대조를 다시 돌려, 기준에 못 미치면 그 수정을 반영하지 않는 것이 회귀 게이트입니다.
> 2차 발표의 실제 동작 시연도 '경주박물관→대릉원→첨성대'로 이어지는 하나의 궤적으로 보고, 각 단계에서 확인할 것을 미리 적어 리허설 체크리스트로 씁니다.

**회귀 게이트의 세 기준**

| 게이트 | 기준 | 현재 결과(직전 점검) |
|---|---|---|
| 앱 단위 시험 | 전부 통과해야 반영 | 179/179 통과(개발 기록 F81·F82) |
| 서버 시험 | 전부 통과해야 반영 | 87/87 통과(개발 기록 F85) |
| 문서 숫자 대조 | 사실 대장 9개 전부 일치해야 반영 | 9/9 일치(추적표 문서 4절) |

*세 기준을 코드 관리 도구로 다시 재는 방법을 자동 프로그램 하나로 모아 두었고(개발 기록 F85), 지금은 커밋 전에 사람이 직접 그 프로그램을 돌려 확인합니다 — 매 수정마다 저절로 돌아가는 장치는 아직 아닙니다.*

안전 게이트는 두 가지입니다.

- 주행 중 입력 차단: 모든 화면에서 글자·사진·금액을 넣는 칸이 비활성화되는지 전 화면을 훑는 점검. 1차 제출 전에 한 차례 끝내는 것이 목표입니다.
- 개인정보 보호: 좌표·차대번호·PIN 같은 개인정보가 코드 어디에도 새는 자리가 없는지 코드를 검색해 위반 0건을 확인하는 점검. 이 세 가지는 이미 코드로 확인했습니다.


### 시연 대본을 하나의 궤적으로 보기

2차 발표의 실제 동작 시연 순서를 코스 그대로 하나의 궤적으로 적고, 단계마다 무엇이 보여야 하는지를 목표 상태로 미리 정해 리허설에서 그대로 확인합니다. 이것은 다섯 번째·여섯 번째 지표(도구 호출 정확도·궤적과 과제 완수)를 시연 준비에 그대로 옮긴 것입니다.

**시연 대본의 단계별 확인 목록**

| 단계 | 확인할 것 | 근거·상태 |
|---|---|---|
| 1. 국립경주박물관 도착 | 스탬프 1/3 기록, 다음 목표 대릉원으로 자동 진행, 퀴즈 2문항·'그때와 지금' 카드 노출 | 에뮬레이터 실측 확인(개발 기록 F49·F74) |
| 2. 대릉원(천마총) 도착 | 스탬프 2/3 기록, 다음 목표 첨성대로 자동 진행 | 에뮬레이터 실측 확인(개발 기록 F74·F77) |
| 3. 첨성대 도착 | 스탬프 3/3 기록, 코스 완주 화면·혜택 미리보기 노출 | 완주 로직 코드 확인, 세 장소 연속 실측은 미확인 |
| 4. 완주 요약 | '오늘의 기록이 저장됐어요' 문구, 요약 타일 노출(값 없으면 타일 숨김) | 코드 구현, 화면 실측 전 |

*3번째 단계의 실제 기기 연속 실측이 남은 과제이며, 리허설에서 이 단계를 가장 먼저 반복해 보는 것이 권장됩니다.*
