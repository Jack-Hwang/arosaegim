# AI 활용 범위 판정

이 문서는 제출 기획서(접수양식)의 별지와 같은 표·같은 문장입니다(커밋 ba96030 기준). 글에 나오는 "본문 N번"·"별지 ○○"은 그 기획서를 가리킵니다. 숫자는 코드에서 센 값이며 코드가 바뀌면 `tools/spec_drift_check.py` 로 다시 대조합니다.


## 1. 아로새김은 어떤 시스템인가

> **한눈에 보기**
> 아로새김에 네 가지 질문(시스템 종류·정답이 있는지·위험이 큰지·지금 개발 단계)을 그대로 적용해 보면, 정해진 규칙과 사람이 미리 써 둔 내용으로 움직이는 앱이고, 판정은 대부분 숫자 비교나 이분법입니다.
> 쓰기 행동이 적고 포인트 캐시백은 전부 시뮬레이션이라 위험은 낮은 편이며, 지금은 1차 서면 심사를 준비하는 단계로 핵심 흐름은 실측을 마쳤고 일부는 재실측이 남아 있습니다.

뒤에 나오는 기술 선택과 적용 범위를 판정하기 전에, 먼저 아로새김이 어떤 종류의 시스템인지부터 네 가지 질문으로 분명히 해 둡니다. 질문 자체는 일반적인 진단 질문이고, 답은 전부 이 앱의 코드와 개발 기록에서 직접 확인한 것입니다.

**아로새김의 시스템 성격 — 네 가지 질문**

| 질문 | 답 | 근거 |
|---|---|---|
| 이 시스템은 어떤 종류인가요? | 정해진 규칙과 사람이 미리 써 둔 내용으로 움직이는 앱입니다. 자유롭게 묻고 답하는 대화형 인공지능이 아닙니다. | 앱 전체에 생성형 모델 호출이 없고(개발 기록 F24), 도착 판정·퀴즈 채점·포인트 캐시백 승인이 모두 규칙 함수입니다[코드 확인]. |
| 정답이 정해져 있나요? | 네. 퀴즈는 미리 정한 보기 번호와 같은지를 비교하고, 도착 판정도 반경 120m 이내인지 아닌지로 딱 갈립니다. | ARO-F3-AC01·ARO-F3-AC02(퀴즈 채점), ARO-F1-AC01(도착 판정). |
| 잘못 판단하면 위험이 큰가요? | 차 안에서 글자를 넣는 곳이 가족 코드 화면 한 곳뿐이고, 포인트 캐시백은 전부 시뮬레이션이라 실제 돈이 오가지 않습니다. 위험은 낮은 편으로 봅니다. | 제품 결정 PD-05, ARO-F8-AC14(화면마다 '포인트 캐시백(예시)'·'현금 아님' 표기), ARO-F8-AC13(차량 화면에 입력칸 없음). |
| 지금 개발 단계는 어디인가요? | 1차 서면 심사를 준비하는 단계입니다. 도착→스탬프→코스 완주로 이어지는 핵심 흐름은 에뮬레이터로 실측을 마쳤고, 정차 화면 자동 전환 재실측 등 일부는 아직 남아 있습니다. | 개발 기록 F72·F74(핵심 흐름 실측), Q26·Q29(남은 재실측). |


## 2. 기술을 고르는 여섯 가지 질문

> **한눈에 보기**
> 기업이 인공지능 기술을 고를 때 흔히 쓰는 여섯 가지 질문(문서 검색·업무 자동화·데이터 통찰·대규모 고객 지원과, 모든 선택에 공통으로 적용하는 데이터 통제·신뢰와 규제 준수 두 가지)을 아로새김에 그대로 대 봤습니다.
> 여섯 질문 모두 '해당 없음' 또는 '이미 다른 방식으로 충족'으로 판정됩니다. 아래 3·4절에서 그 이유를 구체적으로 보입니다.

여섯 질문 가운데 앞의 넷은 '어떤 가치가 필요한가'를 묻고, 뒤의 둘은 어떤 기술을 고르든 공통으로 따져야 하는 통제 질문입니다. 질문마다 판정과 짧은 이유를 적습니다. 자세한 근거는 이어지는 3·4·5절에 있습니다.

**기술 선택 여섯 질문과 아로새김의 판정**

| 질문 | 판정 | 짧은 이유 |
|---|---|---|
| 문서에서 답을 찾아야 하나요? | 해당 없음 | 찾아야 할 자료(경주 코스 3곳의 해설·퀴즈 6문항)가 이미 작고 고정돼 있어 검색 절차 자체가 필요하지 않습니다. |
| 업무를 자동화해야 하나요? | 이미 다른 방식으로 충족 | 도착 판정→스탬프→퀴즈로 이어지는 흐름은 단계가 코드로 고정된 방식으로 이미 자동화돼 있습니다. 여러 인공지능이 역할을 나눠 협업하는 구조는 아닙니다. |
| 데이터에서 통찰이 필요한가요? | 해당 없음 | 포인트·방문 집계는 정해진 규칙으로 더하고 비교하는 계산일 뿐, 앞날을 예측하거나 이상치를 가려내는 모델이 없습니다. |
| 대규모 고객 지원이 필요한가요? | 해당 없음 | 사용 단위가 가족이라는 소수 인원이고, 정차 화면의 맛집·숙소 카드는 장소마다 미리 정해 둔 목록을 그대로 보여 주는 규칙이지 행동을 학습해 순위를 매기는 방식이 아닙니다. |
| 데이터 통제가 필요한가요?(모든 선택에 공통) | 해당 없음 | 애초에 불러 쓰는 생성형 모델이 없어 접근을 통제하거나 비용을 지켜볼 대상이 없습니다(개발 기록 F24). |
| 신뢰와 규제 준수가 필요한가요?(모든 선택에 공통) | 이미 다른 방식으로 충족 | 콘텐츠의 검수 플래그('초안' 표시)와, 의심스러운 제출을 바로 거부하지 않고 적립만 보류하는 포인트 캐시백의 확인 대기 상태가 같은 역할을 합니다. 보류 건을 사람이 들여다보는 절차는 아직 로드맵입니다. |


## 3. 기업용 인공지능 시스템과 선을 그은 지점

> **한눈에 보기**
> 회사가 쓰는 인공지능 시스템 여러 종류를 놓고 아로새김에 하나씩 대 보면, 전부 해당 없음이거나 이미 다른 장치로 충족된 상태입니다. 과장해서 '우리도 AI스럽다'고 말하지 않고, 해당하지 않는 것은 해당하지 않는다고 분명히 적습니다.
> 비슷해 보이지만 실제로는 다른 지점 세 가지(맛집 카드, 영수증 인증, 코스 추천)도 함께 정리했습니다.

위 2절의 여섯 질문은 각각 회사가 흔히 도입하는 여러 인공지능 시스템과 짝지어집니다. 아래 표는 그 시스템 묶음을 아로새김에 하나씩 대 보고, 해당 없음인 이유를 한 줄로 적은 것입니다.

**기업용 인공지능 시스템 묶음과 아로새김의 판정**

| 질문(선택 기준) | 해당하는 시스템 묶음 | 아로새김의 판정과 이유 |
|---|---|---|
| 문서에서 답을 찾아야 하나요? | 문서를 찾아 답하는 검색 보강형 비서, 서류에서 글자를 자동으로 읽어 내는 문서 인식 도구 | 해당 없음 — 영수증 금액도 사람이 숫자로 입력하며, 사진에서 글자를 자동으로 읽어 내는 처리는 하지 않습니다[코드 확인: web/js/screens/receipt.js]. |
| 업무를 자동화해야 하나요? | 업무 자동화 흐름, 여러 인공지능이 역할을 나눠 맡는 구조, 문서를 종류별로 나누는 분류기 | 부분(이미 충족) — 흐름 자동화는 결정적 상태 기계로 돼 있습니다(ARO-F2-AC02, 설계 결정 ADR-005). 역할을 나눈 인공지능 협업은 없습니다(아래 4절). |
| 데이터에서 통찰이 필요한가요? | 수치를 미리 내다보는 예측 모델, 이상한 값을 가려내는 탐지 모델 | 해당 없음 — 포인트·방문 집계는 정해진 규칙으로 더하고 비교하는 계산일 뿐입니다(아래 5절). |
| 대규모 고객 지원이 필요한가요? | 상담을 대신하는 비서, 사용자 행동을 학습해 순서를 매기는 추천 모델 | 해당 없음 — 맛집·숙소 카드는 방문 장소마다 미리 정해 둔 목록을 보여 주는 규칙입니다[코드 확인: backend/app/routers/places.py, ui/parked/ParkedComponents.kt]. |
| 데이터 통제가 필요한가요?(공통) | 모델 접근을 통제하는 문, 호출 비용과 성능을 지켜보는 장치 | 해당 없음 — 애초에 호출하는 생성형 모델이 없어 통제할 대상이 없습니다(개발 기록 F24). |
| 신뢰와 규제 준수가 필요한가요?(공통) | 위험한 출력을 막는 안전장치, 사람이 최종 확인하는 절차 | 이미 다른 장치로 충족 — 검수 전 '초안' 표시(ARO-F3-AC07)와, 적립을 보류만 하고 거부하지는 않는 포인트 캐시백의 확인 대기(ARO-F8-AC08)가 같은 역할을 합니다. 사람이 보류 건을 확인하는 절차 자체는 로드맵입니다. |

*표의 '시스템 묶음'은 회사가 인공지능 기술을 고를 때 흔히 참고하는 여러 범주를 아로새김에 맞게 다시 추린 것이며, 특정 제품명을 가리키지 않습니다.*


### 비슷해 보이지만 실제로는 다른 지점

- **맛집·숙소 카드는 추천 엔진이 아닙니다.** 방문한 장소마다 미리 정해 둔 제휴처 목록을 그대로 보여 주는 규칙이며, 사용자의 과거 행동을 학습해 순위를 바꾸지 않습니다(위 표 4행).
- **영수증 인증은 문서 인식이 아닙니다.** 사진에서 금액이나 글자를 자동으로 읽어 내지 않고, 금액·결제 일시(숙소는 체크인·체크아웃 날짜)를 사람이 직접 입력합니다(위 표 1행).
- **코스 추천은 지금 만들지 않았습니다.** 방문할 수 있는 문화유산이 많아지면 비슷한 코스를 찾아 추천하는 기능을 생각해 볼 수 있지만, 지금 범위에는 없습니다(구현 안 함, 앞으로의 로드맵 후보로만 남겨 둡니다).


## 4. 인공지능 기술별 적용 여부 — 앱 안과 콘텐츠 제작

> **한눈에 보기**
> 생성형 인공지능 직접 호출, 검색 증강 생성(RAG), 그래프 기반 검색 증강, 자율 판단형 검색 증강, 모델 미세조정, 여러 인공지능의 협업까지 여섯 가지 기술을 '차량 안'과 '콘텐츠 제작·운영(차량 밖)'으로 나눠 판정했습니다.
> 결론은 여섯 가지 모두 두 영역 모두에서 적용하지 않음입니다. 자세한 기각 근거와 대안은 설계 결정 기록(제품 결정) PD-01·PD-06에 있습니다.

인공지능을 쓰는 프로그램은 자율성의 정도로 크게 나눌 수 있습니다 — 미리 정한 질문과 답만 주고받는 것, 단계와 순서가 코드로 고정된 것(**워크플로**), 다음에 할 일을 모델이 스스로 정하는 것(**에이전트**)입니다. 아로새김의 핵심 흐름(도착 판정→스탬프→퀴즈→그때와 지금)은 단계가 모두 코드로 고정된 워크플로이고, 다음에 무엇을 할지 스스로 판단하는 에이전트가 아닙니다.

여러 인공지능이 역할을 나눠 협업하게 할지는 세 가지 질문으로 가늠해 볼 수 있습니다 — 작업을 병렬로 나눌 수 있는가, 각자 독립된 맥락에서 일하는가, 나누는 데 드는 비용을 들일 만큼 가치가 있는가.

아로새김의 핵심 로직은 하나의 흐름(주행/정차 상태 하나)을 모든 기능이 함께 쓰므로 세 질문 모두 '아니오'이고, 그래서 아래 표에서도 여러 인공지능의 협업을 쓰지 않는다고 판정합니다[코드 확인: DrivingStateMerger, ADR-005].

생성형 인공지능을 아예 쓰지 않기로 한 결정은 새로 만들지도, 가져다 붙이지도 않는다는 세 번째 선택지에 가깝습니다. 외부 생성형 인공지능 도구를 가져다 붙이려던 계획(Pleos의 생성형 인공지능 연동 도구 Gleo AI)은 그 도구의 제공이 끝나면서 전제 자체가 사라졌고(개발 기록 F24), 그 뒤로 새로 만드는 방안도 검토하지 않았습니다(제품 결정 PD-01).

**인공지능 기술 여섯 가지 — 차량 안과 콘텐츠 제작·운영의 적용 여부**

| 기술 | 차량 안(앱 안) | 콘텐츠 제작·운영(차량 밖) |
|---|---|---|
| 생성형 모델 직접 호출<br>(불러서 그 자리에서 답을 받는 방식) | 적용 안 함 — Pleos가 준비하던 생성형 인공지능 연동 도구는 제공이 끝나 지금 앱은 어떤 생성형 모델도 부르지 않습니다(개발 기록 F24, 제품 결정 PD-01). | 적용 안 함 — 해설·퀴즈 문장은 사람이 공식 자료를 보고 직접 씁니다. 검수 전에는 '초안' 표시를 붙입니다(제품 결정 PD-06, ARO-F3-AC07). |
| 검색 증강 생성(RAG)<br>(미리 모아 둔 자료를 찾아 답에 반영하는 방식) | 적용 안 함 — 차 안에서 자유 질문을 입력하는 화면이 없고(글자를 넣는 곳은 가족 코드 화면 한 곳뿐), 찾을 자료 자체가 코스 3곳·6문항으로 이미 작고 고정돼 있습니다. | 적용 안 함 — 가족의 방문·영수증 기록은 날짜·장소 칸으로 바로 찾아지는 자료라, 문장을 검색해 답을 만드는 절차가 필요하지 않습니다. |
| 그래프 기반 검색 증강<br>(자료 사이의 관계를 미리 그래프로 만들어 두는 방식) | 적용 안 함 — 코스·장소 수가 적어 관계를 그래프로 미리 만들어 둘 만큼 복잡하지 않습니다. | 적용 안 함 — 가족·장소·방문·영수증의 관계는 이미 사람이 설계한 데이터베이스 표 구조로 충분합니다. 인공지능이 문서를 읽어 관계를 자동으로 뽑아낸 것이 아니라는 점을 분명히 둡니다. |
| 자율 판단형 검색 증강<br>(질문마다 다음에 무엇을 찾을지 스스로 계획하는 방식) | 적용 안 함 — 전제인 '주행 중 자유 질문 입력'이 안전 규칙(주행 중 입력 금지)으로 애초에 없습니다. | 적용 안 함 — 콘텐츠를 사람이 쓰고 검수하므로, 여러 단계를 스스로 계획해 자료를 모아야 할 일이 없습니다. |
| 모델 미세조정<br>(말투·형식을 추가로 학습시키는 방식) | 적용 안 함 — 미세조정할 모델 자체를 부르지 않습니다. | 적용 안 함 — 지식이 자주 바뀌면 검색 증강, 말투·형식을 맞추면 미세조정이라는 일반적인 판단 기준에 대 보면, 해설·퀴즈 전량을 사람이 직접 쓰는 아로새김은 둘 다 해당하지 않습니다(학습시킬 자료 자체가 없습니다). |
| 여러 인공지능의 협업<br>(멀티에이전트) | 적용 안 함 — 도착 판정·주행/정차 전환은 하나의 정해진 흐름(상태 기계)을 모든 기능이 함께 따르는 구조라, 작업을 나눠 병렬로 맡길 지점이 없습니다[코드 확인: DrivingStateMerger]. | 적용 안 함 — 콘텐츠는 한 사람이 쓰고 검수하는 과정이라 여러 인공지능이 역할을 나눠 협업할 대상이 없습니다. |

*자세한 기각 대안과 검토 근거는 별지 '명세와 설계 결정'의 설계 결정 기록(제품 결정) PD-01·PD-06에 있습니다. 이 표는 그 결정을 기술 여섯 가지·두 영역으로 다시 펼쳐 놓은 것입니다.*


## 5. 아홉 개 수식과 아로새김이 실제로 쓰는 계산

> **한눈에 보기**
> 인공지능 에이전트 설계에서 흔히 다루는 수식 아홉 개(비용·유사도·거리·생성·선택·학습·협업 계산)는 아로새김 코드 어디에도 쓰이지 않습니다.
> 다만 이름이나 역할이 비슷해 보이는 계산 세 가지(거리 계산, 포인트 비율 곱셈, 단순 합)가 코드에 있어 그 아홉 개와 나란히 비교하고, 왜 같지 않은지 따로 짚었습니다.

아래 두 표는 같은 틀(에이전트 설계에서 흔히 쓰이는 수식 아홉 가지)을 기준으로 삼습니다. 첫 표는 아로새김이 실제로 코드에서 계산하는 세 가지이고, 둘째 표는 그 아홉 가지 수식입니다. 아홉 가지는 모두 코드에 쓰이지 않으며, 수치는 전부 코드에서 직접 확인했습니다.

**실제로 쓰는 계산 세 가지**

| 계산 | 쓰는 곳 | 근거 |
|---|---|---|
| 거리 계산(두 좌표 사이의 실제 거리, 단위 m) | 목적지 반경 120m 안에 들어왔는지 판정합니다. 근접 알림이 실패하면 이 계산으로 거리를 직접 구합니다. | [코드 확인] Haversine.distanceM, FusedArrivalDetector 폴백 모드, ARO-F1-AC01·AC02 |
| 포인트 비율 곱셈(결제액 × 1~2%) | 영수증 결제 금액에 제휴처별로 정해 둔 비율(1% 또는 2%)을 곱하고 소수점 이하를 버려 적립 포인트를 정합니다. | [코드 확인] backend/app/services/points.py, ARO-F8-AC01 |
| 단순 합(가중치 없이 그대로 더하기) | 가족의 포인트 총합은 적립된 포인트를 그대로 더한 값이고, 좌석 점유 인원도 응답한 좌석의 값을 그대로 더한 값입니다. | [코드 확인] ARO-F8-AC11, countOccupied(개발 기록 F82) |

**쓰지 않는 계산 — 이름은 비슷해도 다른 이유**

| 수식 | 쓰지 않는 이유 |
|---|---|
| 토큰 수·호출 비용 계산 | 불러 쓰는 생성형 모델 자체가 없어 호출 비용을 셀 일이 없습니다. '글자 수 → 대략적인 토큰 수' 감각만 참고해 화면 문장 길이 제한(두세 줄 이내)이 적당한 분량인지 가늠하는 데만 썼습니다(수치는 추정이며 실제로 토큰을 세지는 않았습니다). |
| 의미 유사도(두 의미 벡터가 얼마나 비슷한지 재는 값) | 의미 벡터(임베딩)를 만들어 비교하는 절차가 없습니다. 코스가 많아져 비슷한 코스를 추천하는 기능이 필요해지면 참고할 수 있는 로드맵 후보로만 남겨 둡니다(구현 안 함). |
| 벡터 거리(의미 벡터 공간에서 두 점 사이를 재는 거리) | 이름은 '거리'로 같지만 의미가 다릅니다. 아로새김이 쓰는 거리는 위 표의 지구 표면 실제 위치 거리이고, 이 수식은 의미 벡터 사이의 거리입니다. |
| 생성형 모델이 다음 글자를 고르는 계산(주의 가중치·다음 토큰 확률) | 생성형 모델을 호출하지 않으므로 다음 글자를 확률로 고르는 절차 자체가 일어나지 않습니다. |
| 도구(다음 행동) 선택 확률 계산 | 아로새김의 다음 화면·다음 단계는 정해진 규칙(상태 기계)으로 바로 정해지며, 여러 후보 중 확률이 가장 높은 것을 고르는 절차를 거치지 않습니다. |
| 학습하며 행동을 고치는 계산(보상을 보고 배우는 방식과 먼 미래 보상까지 더하는 계산) | 스스로 경험을 쌓아 가며 판단을 바꾸는 학습 과정이 없습니다. 퀴즈 정답·포인트 캐시백 승인 기준은 모두 사람이 미리 정한 고정 규칙입니다. |
| 여러 인공지능의 성과를 가중치로 합치는 계산 | 위 표의 '단순 합'과 모양은 비슷해 보이지만, 아로새김의 포인트 총합에는 가중치가 없고 여러 인공지능의 성과를 평가하려는 목적도 아닙니다. 수식의 틀만 비교 대상으로 가져왔을 뿐 그대로 쓰지는 않았습니다. |

다른 자료에는 단순한 대화형 호출을 1배로 두면, 혼자 판단하는 생성형 인공지능 호출은 그 4배, 여러 인공지능이 협업하면 15배까지 비용이 커진다는 감각이 있습니다. 이 배수는 생성형 모델을 실제로 호출하는 비용을 전제로 한 것입니다.

생성형 모델을 전혀 호출하지 않는 아로새김에는 이 배수를 그대로 적용하지 않습니다. 다만 '기능을 더 자동화하거나 여러 인공지능으로 나누자'는 제안이 들어오면 비용과 복잡도가 함께 커진다는 방향성만 판단 기준으로 참고합니다.

*참고: 생성형 모델이 다음 글자를 고를 때 무작위성의 정도를 조절하는 값(디코딩 파라미터)이라는 개념도 쓰지 않습니다. 안내 음성은 사람이 미리 고르고 녹음한 파일을 그대로 재생하므로 무작위성의 정도를 정할 자리가 없습니다.*


## 6. 고영향 인공지능 점검은 어디에 있는가

> **한눈에 보기**
> 사람에 대한 채용·신용·민원·의료 같은 중대한 결정에 영향을 주는 '고영향 인공지능'에 해당하는지는 이 별지가 아니라 별지 '명세와 설계 결정'의 '고영향 AI 점검' 절에서 다룹니다.
> 그 별지의 결론과 이 별지 4절의 판정(생성형 모델을 전혀 부르지 않는다는 점)은 같은 방향입니다. 법률 검토를 거치지 않은 자체 점검이라는 점은 그 별지에 그대로 남아 있습니다(미확인).

좌석 점유 합산, '그때와 지금' 비교, 퀴즈 채점, 포인트 캐시백 승인·거부, 콘텐츠 제작이라는 다섯 지점을 하나씩 살펴 모두 숫자 비교이거나 미리 정한 규칙 판정임을 확인한 결과는 별지 '명세와 설계 결정'의 '고영향 AI 점검' 절에 있습니다.

이 별지는 그 결론을 다시 풀어 쓰지 않고, 위 4절의 판정(여섯 가지 인공지능 기술 모두 적용하지 않음)이 그 결론과 어긋나지 않는다는 것만 짚어 둡니다.
